# MySQL 索引原理：B+树、聚簇与二级、回表与覆盖、最左前缀与失效场景

> 摘要：索引是 MySQL 性能优化的第一抓手，但"建索引"远不是"加个 KEY"那么简单。本文从 InnoDB 的存储结构讲起：为什么 B+树能把千万级数据压到 2~4 层、聚簇索引与二级索引叶子节点各存什么、回表和覆盖索引怎么发生、每建一个二级索引为什么就多一棵树，最后落到最左前缀与 8 种典型索引失效场景。全部结合本项目订单表的真实索引设计展开。

## 一、为什么要这样做（业务背景与痛点）

不带索引的查询是"全表扫描"：把整张表的每个数据页从磁盘读出来，逐行比对条件。数据量小的时候无所谓，但秒杀订单表会持续增长，商户查询、用户查询都是高频操作，每次全扫的磁盘 IO 成本会线性上涨。

索引解决的核心问题只有一个：**把"全表扫描"变成"按树定位"**——让查询沿着 B+树从根到叶子走 2~4 层，只读少数几个页，就能找到目标数据。但索引不是免费的：每建一个索引，写入时就要多维护一棵树，磁盘和内存都要多占空间。所以必须理解它的原理，才能决定"建什么、建几个、为什么不建"。

## 二、用什么方法解决（方案对比）

| 方案 | 查找复杂度 | 磁盘 IO | 范围/排序 | 说明 |
|---|---|---|---|---|
| 全表扫描 | O(N) | N 个页 | 支持 | 无索引时的兜底 |
| 哈希索引 | O(1) | 1 次 | ❌ 无序 | InnoDB 仅用自适应哈希索引做辅助 |
| 二叉树 | O(log₂N) | ~24 层（千万级） | 支持 | 树太高，IO 次数太多 |
| B+树 | O(log_d N)，d≈1000 | **2~4 层** | ✅ 叶子有序链表 | InnoDB 默认，最优 |

**B+树为什么赢**：每个节点是一个 16KB 磁盘页，能装约 1000 个 key（扇出 d≈1000），所以树高 = log₁₀₀₀(N)。1000 万行的表只有 2~3 层 = 2~3 次磁盘 IO；而二叉树要 24 层 = 24 次 IO。**层数即磁盘 IO 次数**，这是 B+树快的本质。哈希虽然等值查找 O(1)，但无法范围查询、无法排序，所以只能当辅助。

## 三、为什么需要这个技术（原理深入）

### 3.1 两类索引：叶子节点存的东西完全不同

- **聚簇索引（主键索引）**：每表一个，叶子节点存**整行数据**。表数据本身就按主键排序存在这棵树的叶子里——"表"和"主键索引"是同一个东西。没有主键时 InnoDB 用第一个非空唯一键，再没有就隐藏生成 6 字节 rowid。
- **二级索引**：其他所有索引，每建一个就是一棵新树，叶子节点只存**索引列 + 主键值**（轻量投影，不是整行副本）。

本项目订单表的索引全景：

```sql
CREATE TABLE `tb_voucher_order` (
  `id` bigint(20) NOT NULL,
  ...
  PRIMARY KEY (`id`),                                      -- 树1：聚簇，叶子=整行
  UNIQUE KEY `uk_user_voucher` (`user_id`, `voucher_id`),  -- 树2：二级，叶子=[user_id,voucher_id,id]
  KEY `idx_shop_create_time` (`shop_id`, `create_time`)     -- 树3：二级，叶子=[shop_id,create_time,id]
) ENGINE = InnoDB;
```

### 3.2 回表：二级索引缺数据，拿主键回聚簇索引补

二级索引叶子只有"索引列 + 主键"。查询需要其他列时，必须拿主键再去聚簇索引查整行——这就是回表（一次随机 IO）。

```sql
-- 需要 status，但 status 不在 uk_user_voucher 里 → 回表
SELECT status FROM tb_voucher_order WHERE user_id = ? AND voucher_id = ?;
-- 执行：二级索引定位到叶子 [user_id,voucher_id,id] → 拿 id 回聚簇索引 → 取 status
```

### 3.3 覆盖索引：要的列全在索引里，免回表

如果查询所需列全在二级索引里（索引列 + 主键），就不需要回表——这就是覆盖索引。本项目里这条查询天然覆盖：

```java
// SELECT COUNT(*) FROM tb_voucher_order WHERE user_id=? AND voucher_id=?
query().eq("user_id", userId).eq("voucher_id", voucherId).count()
```

InnoDB 只需要数二级索引树上的叶子条数，叶子节点里就有答案，**零回表**。对比：`SELECT *` + 二级索引条件几乎必回表；只查索引列则免回表。

### 3.4 每建一个二级索引 = 多一棵树，代价是写放大

二级索引树越多：INSERT 每插一行要往每棵树各写一条；UPDATE/DELETE 同步维护；磁盘和 Buffer Pool 都要多占。这就是"索引不是越多越好"的原因——**用写性能和空间换读性能**。所以约束类索引（UNIQUE/PRIMARY KEY）与数据量无关必须建（它们是业务正确性保证，加速只是副产品）；加速类索引用 EXPLAIN 成本模型说了算——小表全扫只要几十次 IO 时，索引常常"白建"。

### 3.5 最左前缀：复合索引的使用规则

`(A, B, C)` 复合索引的叶子按"整体最左列、组内下一列"排序。能用到的形态：

- `A=?` ✅；`A=? AND B=?` ✅；`A=? AND B=? AND C=?` ✅；
- `A=? AND C=?` ⚠️ 只用 A（B 被跳过，C 用不上）；
- `B=?` 或 `C=?` ❌ 索引用不上（不是全局有序）。

对应项目的 `idx_shop_create_time (shop_id, create_time)`：
- `WHERE shop_id=?` 走索引 ✅；
- `WHERE shop_id=? AND create_time BETWEEN ...` 走索引 ✅（组内范围）；
- `WHERE create_time=?`（不带 shop_id）❌ 用不上。

### 3.6 8 种典型索引失效场景

1. **违反最左前缀**：跳过索引最左列；
2. **索引列上做函数运算**：`WHERE DATE(create_time)=...` 失效，改写为范围比较即可走索引；
3. **隐式类型转换**：varchar 列传数字比较，列被套转换 → 失效（字符串必须加引号）；
4. **前导模糊查询**：`LIKE '%xx'` 失效，`LIKE 'xx%'` 可用；
5. **负向查询**：`!=`、`NOT IN`、`NOT LIKE` 通常失效；
6. **OR 连接**：多条件无法同时用一棵树，常退化为全扫（可拆 UNION）；
7. **对索引列做运算**：`WHERE id+1=100` 失效，值算好再比（`id=99`）；
8. **范围条件之后的列**：`A=? AND B>? AND C=?` 中 C 用不上（范围后的列断掉）。

用 `EXPLAIN` 的 `key_len` 验证：key_len 越长，用到的索引列越多（只用了第 1 列时 key_len 就是 1 列的长度）。

## 四、不用这个技术怎么办（替代方案与当前边界）

- **不用索引**：回到全表扫描，数据量一大 IO 线性膨胀，热点查询直接拖垮数据库；
- **用错索引**：索引列顺序与查询条件不匹配、列上套函数、隐式转换——索引建了也白建，反而白付写放大代价；
- **索引过载**：给所有列都建索引，INSERT/UPDATE 性能被写放大拖垮，Buffer Pool 被索引页挤占。

**当前边界（本地学习项目）**：本项目订单表只有 2 个二级索引，配合"按用户+券查、按主键查、按商户+时间汇总"三个真实查询场景，是克制的设计；商户/用户等小表主要靠主键聚簇索引，不需要为它们堆二级索引。

**工程建议**：约束类索引必须建；加速类索引先用 `EXPLAIN` 验证 `type` 与 `key_len` 再决定；复合索引字段顺序按"等值列在前、范围列在后"排列，并检查查询是否命中最左前缀。

## 小结

1. B+树节点 = 16KB 磁盘页，扇出约 1000，千万级数据也只有 2~4 层——**层数即磁盘 IO 次数**，这是它优于二叉树和哈希（范围查询）的本质。
2. 聚簇索引叶子存整行（每表一个），二级索引叶子存"索引列 + 主键"（每建一个就多一棵树）。
3. 回表 = 二级索引缺列拿主键再查聚簇索引（一次随机 IO）；覆盖索引 = 所需列全在二级索引里免回表。
4. 索引用写放大换读性能：约束类必须建，加速类用 EXPLAIN 决定，小表全扫常常已经够快。
5. 复合索引受最左前缀约束，范围条件之后的列用不上。
6. 8 种失效场景核心就一句话：**让索引列保持"裸列"参与比较，别套函数、别隐式转换、别破坏最左顺序**。
