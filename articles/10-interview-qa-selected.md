# 高频面试问答精选：黑马点评改造项目（业务侧 + 实时数仓侧）

> **导读**：本文从项目面试问答库中筛选 40 个最有代表性的问答，按主题分组整理。适用范围：准备"本地生活 + 实时运营平台"类项目的面试，或复盘黑马点评改造项目的技术点。统一口径是**个人学习项目**，业务功能按"学习项目已实现"表达，实时链路只在单机 Docker Compose 环境验证，所有问答都不夸大、不编造压测数据。回答结构建议按"先结论 → 再讲项目实现 → 最后主动说明边界"展开，这里的答案已压缩到 60—150 字，面试前请再展开成 30—60 秒口述。最后附"面试时最容易说错的 18 句话"，原文保留，建议背熟。

## 一、认证与链路追踪

**问：JWT 双 Token 的完整认证链路是什么？**

答：登录先校验 Redis 验证码，签发 30 分钟 HS256 accessToken；随机 refreshToken 对应的用户摘要以 Hash 存 Redis，TTL 7 天。普通请求只验 JWT 不查 Redis，拦截器把用户放进 ThreadLocal，请求结束统一 `remove()`；accessToken 过期后用 refreshToken 续签。退出只删 refreshToken，已签发的 accessToken 仍有效到自身过期。

**问：JWT 已经无状态，为什么还用 Redis？**

答：Redis 不参与每次 accessToken 鉴权，只保存 refreshToken 会话，使续期、退出和会话过期可控。这样普通请求保持无状态和低延迟，同时保留有限的服务端会话管理能力。

**问：JWT 能放手机号、权限等敏感信息吗？**

答：不建议。JWT 默认只是 Base64URL 编码、不是加密，客户端可以读取载荷。当前只放用户 ID、昵称、头像和时间字段；敏感信息不进 Token，权限用稳定标识并在服务端校验，避免权限变化后旧 Token 长期有效。

**问：TraceID、MDC 和 AOP 的链路是什么？**

答：order 0 的拦截器优先读取请求头 TraceID，没有就生成 UUID 写入 MDC 和响应头；Controller AOP 在正常和异常场景记录 URI、成功标志与耗时；请求完成后移除 MDC。当前没有 Span、跨服务采样，也没有把上下文传播到 Kafka、RabbitMQ 或线程池，准确口径是"请求级链路日志"。

## 二、缓存

**问：Caffeine + Redis 二级缓存怎样读写和失效？**

答：查询顺序是 Caffeine L1 → Redis L2 → MySQL，命中下层就向上回填；L1 最多 1 万条、30 秒过期，L2 正常数据 30 分钟，不存在数据用 2 秒空值防穿透。更新在数据库提交后清本机 L1、删 L2，再用 Pub/Sub 通知其他实例清 L1。只保证最终一致，漏广播由 L1 短 TTL 兜底。

**问：互斥重建和逻辑过期当前启用了吗？**

答：两种方法都有实现，但当前 `queryById` 主链路只启用了空值缓存 pass-through，它解决穿透，却没有解决热点 Key 同时失效后的并发回源。互斥锁和逻辑过期属于已写出的替代方案，不能说三个策略同时在线生效。

**问：穿透、击穿、雪崩分别怎么处理？**

答：穿透用短 TTL 空值缓存（数据量更大时可上布隆过滤器，当前未落地）；击穿用互斥锁重建或逻辑过期；雪崩用随机 TTL、缓存预热、Redis 高可用以及限流熔断。当前主链路只有空值缓存，互斥和逻辑过期未启用。

**问：多实例 Caffeine 怎样保持一致？**

答：更新提交后发布失效 Key，各实例订阅 Redis Pub/Sub 并删除本地缓存。延迟低、实现简单，但消息不持久，订阅者断线可能漏消息，所以依赖 30 秒本地 TTL 兜底；生产环境可改为可靠 MQ、binlog 订阅或带版本号的缓存读取。

## 三、秒杀

**问：秒杀从请求进入到订单落库，完整链路是什么？**

答：先生成订单 ID，Redis Lua 原子校验库存和一人一单并预扣；成功后 `offer` 写入本地有界队列，单线程消费者取任务后加用户维度 Redisson 锁，事务里条件扣库存防超卖、唯一索引防重复。接口返回订单 ID 只表示受理。当前队列不持久，入队、抢锁或落库失败没有补偿，只能叫本地削峰验证。

**问：Lua 脚本为什么原子？报错会自动回滚吗？**

答：Redis 执行脚本期间不会插入其他命令，所以"查库存、查资格、扣库存、记资格"不可被打断；但原子执行不等于事务回滚，脚本中途报错不会撤销已执行的写命令。因此要先完成全部校验再写。当前脚本也是先校验后写，但库存 Key 缺失时 `tonumber(nil)` 会报错，初始化仍需补强。

**问：`stock > 0` 算乐观锁吗？**

答：它没有 version 字段，不是经典版本号乐观锁，但属于基于条件更新的乐观并发控制：先尝试原子修改，再根据受影响行数判断竞争是否成功，数据库不会把库存扣成负数。

**问：本地队列满时 `add/offer/put` 有什么区别？**

答：`add` 满时抛异常，`offer` 立即返回 false，`put` 阻塞等待。项目用 `offer`，不会长期占住请求线程；但 Lua 已预扣后入队失败没有补偿，用户会被占库存且无法重试。队列容量虽然是有界的，但百万级对象仍有明显内存风险，生产中要按对象大小和峰值重新定容量。

**问：为什么异步下单没用 RabbitMQ（或 Kafka）？**

答：秒杀仍保留学习阶段的本地队列实现，用来先验证"Lua 前置校验、请求快速返回、异步落库"主链路，尚未完成可靠消息化改造。异步下单是业务命令，更需要 ACK、重试、死信和补偿；Kafka 已用于分析事件流，职责更清晰，不是为少引入组件而省略。

## 四、Feed 与消息

**问：Feed 是推、拉还是推拉结合？**

答：当前是纯推模式，适合粉丝规模不大的普通用户：发布成本增加，但读取快。大 V 会产生写放大，生产环境应对普通用户继续推，对大 V 改为读时拉取或推拉结合，并设置收件箱容量和过期策略。

**问：滚动分页为什么用 `max + offset`？**

答：下一页把上一页最小 score 作为新的 max；若上一页边界仍是同一个 score，就把本次同分条数与旧 offset 累加，否则重新计数。这样比页码分页更能抵抗新 Feed 插入。但当前代码把这个三元分支写反，会在全同分时重复、跨 score 时多跳，修复并补测前不能讲闭环。

**问：事务提交后、消息发送前宕机，消息会丢吗？**

答：会。`afterCommit` 只能避免事务回滚后误发；数据库已提交、回调尚未发出时进程宕机，消息仍会丢。Outbox 方案是在同一数据库事务中写业务数据和事件，由独立投递器或 CDC 读取并投递，消费者再用业务唯一键保证幂等，形成最终一致闭环。

**问：通知为什么用 RabbitMQ，行为流用 Kafka？**

答：通知是低到中吞吐的业务消息，重视路由、ACK、重试和死信；行为日志是高吞吐、可回放的事件流，要供多个 Flink 作业用不同消费组独立读取，更适合 Kafka。二者不是重复堆技术，而是服务不同语义。

## 五、实时数仓架构

**问：行为为什么直写 Kafka，订单走 CDC？**

答：浏览、曝光天然是事件，量大且不一定需要进业务库，直写 Kafka 延迟更低，也避免给 MySQL 增加大量写压力；订单是核心交易事实，必须先由 MySQL 事务保证正确，再通过 CDC 分发状态变化。分析链路不能反过来成为订单事实源。

**问：为什么在 MySQL 和实时计算之间放 Kafka？**

答：解耦和削峰——业务应用只负责发送行为事件，不需要等待下游聚合完成，Flink 按自己的消费能力处理；Kafka 保留可回放的事件日志，计算逻辑修改或任务恢复时可重新消费；多个质量检测和聚合作业也能通过不同消费组独立读取同一主题。Kafka 不能替代业务库，最终状态仍以 MySQL 为准。

**问：为什么用 Flink SQL 而不是全部用 DataStream？**

答：当前任务以过滤、去重、分组聚合和结果写出为主，关系表达清晰，SQL 开发成本更低，也便于查看执行计划。复杂自定义状态、异步 I/O、精细定时器等 SQL 难以表达的规则才用 DataStream API。选型依据是问题表达，不是 SQL 一定比代码快。

**问：ODS、DWD、DWS、ADS 分别负责什么？为什么分层？**

答：ODS 保留原始行为和 CDC 变更；DWD 做校验、统一 user_key、按 event_id 去重和脏数据分流；DWS 按主题维护日粒度聚合；ADS 用 Doris 视图组合指标。分层后 DWD 可复用、DWS 统一口径、ADS 只做展示组合，问题能逐层定位；一条 SQL 算到 ADS 会让清洗、口径和展示逻辑耦合。

## 六、Kafka

**问：Topic、Partition、Consumer Group 分别是什么？**

答：Topic 是消息的逻辑分类；Partition 是并行读写和局部顺序的基本单位，同一 Partition 内有序；Consumer Group 是一组协作消费者，同组内一个 Partition 同一时刻只由一个消费者处理，不同消费组可以独立读取同一 Topic。

**问：Kafka 消息的 Key 应该如何选择？**

答：需要同一业务实体有序时，选择稳定业务 ID 作 Key，例如 `event_id`、`order_id`、`voucher_id`；当前埋点按 userId 优先、deviceId 次之、eventId 兜底，获得用户维度局部有序，但热点用户可能倾斜。Upsert Kafka 必须通过主键表达更新语义。

**问：Consumer Lag 上涨如何排查？**

答：排查顺序：消费者是否存活、Flink 是否反压、Checkpoint 是否长期失败、各分区 Lag 是否均匀（少数分区高先查 Key 倾斜）、Doris Sink 是否变慢、网络磁盘是否异常。恢复后还要观察 Lag 是否持续回落，确认消费能力已追上来。

**问：Kafka 能保证消息不丢吗？**

答：要看完整配置和故障范围。生产端需确认 ACK、重试和幂等配置；Broker 需合理副本数和 `min.insync.replicas`；消费者要正确管理 Offset。当前本地 Kafka 副本数为 1，只适合演示，不能抵御节点级数据丢失。

## 七、Flink

**问：Flink CDC 的工作原理是什么？**

答：MySQL CDC 首次启动读取存量快照并记录一致的 binlog 位点，快照完成后从对应位置持续消费 row 格式 binlog 增量，转成 Flink Changelog；订单表声明业务主键。前置条件：MySQL 开启 row 格式 binlog，CDC 账号需要 SELECT、RELOAD、SHOW DATABASES、REPLICATION SLAVE、REPLICATION CLIENT 权限。

**问：CDC 的 update_before/update_after 怎样处理？**

答：CDC 在 Flink 中形成 Changelog，主键表的更新以撤回旧值、加入新值或 upsert 语义向下游传播；Upsert Kafka 以主键为消息 Key，Doris Unique Key 保存最终版本；聚合算子对旧贡献撤回、对新贡献累加。

**问：行为事件怎样去重，状态保留多久？**

答：DWD 按 event_id 分区，用 `ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY event_ts)` 保留最早一条；Doris 明细表再以 event_id 为 Unique Key 收敛。状态空闲 TTL 2 天，按处理时间清理，不等于"事件时间满两天"；同 ID 同 event_ts 还缺稳定 tie-breaker。

**问：Watermark 到底做什么？**

答：Watermark 是算子对事件时间进度的估计，用于事件时间窗口触发和迟到判断。项目定义 `event_ts − 10 秒`，表示 Watermark 比已观测最大事件时间落后约 10 秒；它不等于自动容忍 10 秒迟到。当前 DWS 是自然日持续分组聚合，不靠 Watermark 关闭日窗口。

**问：能保证端到端 Exactly-Once 吗？**

答：分段回答：Flink 配置 Exactly-Once Checkpoint，Kafka Source 位点随 Checkpoint 保存，Doris Sink 开启 2PC 且表为 Unique Key，可降低恢复后重复写入的风险；但端到端语义还取决于应用生产端、CDC、Sink 事务提交和恢复方式，所以只承诺"降低重复和丢失风险"，不笼统说绝对 Exactly-Once。

## 八、Doris

**问：为什么使用 Unique Key 模型？**

答：CDC 订单和实时聚合结果会持续更新，同一订单 ID 或"日期 + 业务维度"会多次写入；Unique Key Merge-on-Write 按业务主键覆盖最新版本，也能降低任务恢复重放产生的重复结果。当前桶数只有 1 或 3，是单节点演示配置，不是生产分桶方案。

**问：Doris Sink 的 2PC 怎么理解？**

答：Sink 在 Checkpoint 期间先预提交本批数据，Checkpoint 成功后再提交事务，失败则该批不作为成功结果提交，把外部写入与 Flink Checkpoint 对齐。Unique Key 是幂等兜底，不等于替代 2PC；2PC 还依赖稳定 Label，提交脚本为每次部署追加唯一 Deployment ID 避免 Label 冲突。

**问：DWS 表和 ADS 视图有什么区别？**

答：DWS 表保存可复用的主题聚合结果，如商户日汇总、券日汇总、订单日汇总，粒度即 Unique Key；ADS 用 Doris 视图按看板口径关联计算（排行榜权重、漏斗、留存），修改展示公式时不必重算 DWD 明细。

## 九、质量对账与故障

**问：项目做了哪些数据质量检查？**

答：行为侧检查事件 ID、类型、用户标识、业务 ID、时间，早于 7 天或晚于 5 分钟判异常；订单侧检查状态 1—6、金额非负、实付加优惠不超过券面、退款不超过实付、支付/退款时间；券侧检查商户、类型、状态和金额关系。非法行为写入 dirty Topic，质量结果按分钟写入 `ads_data_quality`。

**问：为什么既要实时质量检测，又要离线对账？**

答：实时检测能快速发现单条数据的格式和业务规则问题，但不能证明最终指标一定正确；对账从业务事实源与分析汇总两端独立计算同一口径，可以发现 CDC 漏数、任务积压、聚合错误和写入异常。两者解决的问题不同。

**问：MySQL 与 Doris 怎样对账？**

答：按指定日期分别查询 MySQL 订单表和 Doris `dws_order_day`，比较订单数、已支付订单数、GMV 和退款金额。有差异时先检查 Kafka Lag、Checkpoint 状态和非法订单质量记录，再判断是数据尚未到达还是计算口径错误。保存的样本为 40 笔订单、30 笔已支付、GMV 142,500 分，差异为 0，只证明该样本口径一致。

**问：TaskManager 宕机后怎样做恢复验证？**

答：重启容器后作业从最近 Checkpoint 恢复算子状态和 Kafka 位点；成功条件为新 TaskManager 注册、作业 RUNNING、恢复后新 Checkpoint 成功、Lag 回落至 0、事件全部写入 Doris。核心 DWD 演练：约 23.8 秒恢复 RUNNING、37.8 秒内新 Checkpoint、50.9 秒内 Lag 清零，2 万条事件无丢失；DWS 全量历史重放未验证。

## 十、高频 Java 八股

**问：线程池的核心参数和执行流程是什么？**

答：corePoolSize、maximumPoolSize、keepAliveTime、workQueue、ThreadFactory 和拒绝策略。任务先创建核心线程，再入队；队列满后才创建非核心线程，线程数到最大且队列也满时触发拒绝。项目秒杀任务用有界 `ArrayBlockingQueue`，但缓存重建用 `newFixedThreadPool(10)`，其内部队列无界，是需要继续改造的风险点。

**问：ThreadLocal 为什么会串数据或泄漏？**

答：数据放在线程自己的 `ThreadLocalMap` 中，Entry 的 key 是弱引用、value 是强引用；线程池线程长期存活，忘记 `remove()` 会让旧 value 被后续请求读到或无法回收。项目在 JWT 拦截器的 `afterCompletion` 清理用户上下文、TraceID 拦截器清理 MDC；异步线程应显式传参并在 `finally` 清上下文。

**问：消息可靠投递为什么要分三段回答？**

答：生产端需要 confirm、发送回调和有限重试；Broker 需要持久化消息与队列，并配置副本；消费者应业务成功后再 ACK，失败进入有界重试和死信。这样通常得到至少一次投递，所以还必须用业务唯一键、状态机或数据库约束保证消费幂等。当前项目 RabbitMQ 尚未补齐这些能力。

## 附：面试时最容易说错的 18 句话

1. 不说"生产系统"，说"个人学习项目，在本地单机/容器环境完成验证"。
2. 不说"全链路追踪"，说"单体 HTTP 请求级 TraceID 日志"。
3. 不说"普通请求会查 Redis 会话"，当前 accessToken 鉴权只解析 JWT。
4. 不说"退出后 Token 立即失效"，当前旧 accessToken 仍能活到过期。
5. 不说"商户查询同时用了空值、互斥锁和逻辑过期"，当前主链路只启用空值缓存。
6. 不说"Pub/Sub 保证缓存消息不丢"，它没有持久化和补发。
7. 不说"秒杀用了 RabbitMQ"，当前是 JVM 本地阻塞队列。
8. 不说"秒杀受理就是订单成功"，最终成功必须以 MySQL 订单为准。
9. 不说"异步秒杀已校验活动时间"，当前主入口没有 begin/end 校验。
10. 不说"Redis 预扣成功后的异常已有补偿"，当前入队、抢锁和落库失败都没有完整补偿。
11. 不说"RabbitMQ exactly-once"，当前连 confirm、幂等和死信都未补齐。
12. 不说"Feed 同分滚动分页已正确处理"，当前 offset 累计分支写反，修复并补测后再讲闭环。
13. 不说"整条实时链路绝对 exactly-once"或"生产可达 986 events/s"，只能引用固定单机环境的实测结果和边界。
14. 不说"`latency_ms` 是端到端延迟"，当前只计算 ingestTime 减 eventTime。
15. 不说"DAU 覆盖所有下单用户"，当前 DAU 只来自合法行为事件。
16. 不说"请求数等于 accepted + rejected"，队列满的 `ERROR` 当前不计入两者。
17. 不说"GMV 按支付日统计"，当前按订单 createTime 归属日期，退款金额另列。
18. 不说"properties 中的扩展字段都进入 DWD"，当前只显式提取 reason，followUserId 会丢失。
