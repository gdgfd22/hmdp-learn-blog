# 项目总览：从黑马点评到个人改造的学习项目

> 摘要：本文介绍这个学习项目的全貌——它由黑马点评课程项目改造而来，在原有商户、博客、关注、秒杀等业务骨架之上，逐步加入了 JWT 双 Token 认证、请求级 TraceID 日志、Caffeine 二级缓存、RabbitMQ 社交通知，以及一套 Kafka + Flink + Doris 的实时数仓分析链路。本文讲清楚"为什么做"、整体架构、技术栈和当前边界。

## 一、为什么要这样做（业务背景与痛点）

黑马点评是一个本地生活服务平台，业务上包含登录认证、商户信息、博客、关注关系、优惠券秒杀等模块。它是学习 Spring Boot 后端开发的经典项目，但课程代码解决的是"单机、单实例、功能可用"的问题，距离真实生产还有几个明显的痛点：

1. **认证不可扩展**：课程默认用 Session 保存登录态，Session 存储在单个 Tomcat 的内存里。一旦多实例部署，用户请求落在不同实例上就会"掉登录"。
2. **缓存太简单**：商户详情是典型的高频读、低频写数据，课程里直接查 MySQL，热点数据下数据库压力很大；后来引入 Redis 缓存，又面临缓存穿透、击穿、雪崩等一系列经典问题。
3. **秒杀靠数据库硬扛**：优惠券秒杀是高并发场景，如果每次都先查库存、再扣库存、再下单，超卖和数据库写压力都无法避免。
4. **日志无法串联**：一个请求经过拦截器、Controller、Service、DAO 多层调用，出了问题很难把日志串成一条线。
5. **业务与分析不分家**：运营想看商户热度、内容排行、优惠券漏斗，如果直接在 MySQL 上做多维聚合，会干扰在线交易（OLTP）。

作为个人学习项目，我给自己定的目标不是"跑通功能"，而是**把课程代码升级成一套能讲清楚"为什么这么设计"的完整系统**，覆盖认证、缓存、高并发、异步解耦、链路追踪和实时数仓这几个面试高频方向。

## 二、用什么方法解决（方案对比）

针对上述痛点，逐项对比后选择的方案如下：

| 痛点 | 候选方案 | 本项目选择 | 选择理由 |
|---|---|---|---|
| 登录态共享 | Session 拷贝 / Redis 存 Session / JWT | JWT + Redis refreshToken 双 Token | 普通请求无状态、低延迟，Redis 只管会话续期与退出 |
| 日志串联 | 手动拼参数 / Filter / Interceptor + MDC | TraceID + MDC + AOP 切面 | 拦截器统一生成 TraceID，AOP 统一记录接口耗时 |
| 商户缓存 | 只查 MySQL / Redis 单层 / Caffeine+Redis | Caffeine L1 + Redis L2 二级缓存 | L1 本地内存命中更快，L2 多实例共享 |
| 秒杀 | synchronized / 数据库乐观锁 / 分布式锁 + 异步队列 | Lua 前置校验 + Redisson 锁 + 本地阻塞队列削峰 | Lua 原子完成校验与预扣，异步落库减少数据库瞬时压力 |
| 社交通知 | 同步调用 / 本地队列 / MQ | RabbitMQ 异步通知 | 点赞、评论、关注通知与主链路解耦 |
| 实时分析 | MySQL 直接聚合 / 离线数仓 / 实时数仓 | Kafka + Flink + Doris | 行为流与业务事实分离，OLTP 与 OLAP 负载隔离 |

整体架构上，业务系统与分析系统分开：

```text
业务侧：浏览器 → Nginx → Spring Boot（JWT 认证 / 二级缓存 / 秒杀 / Feed / 通知）
          └── 行为事件 → Kafka ODS
          └── MySQL 订单/优惠券表 → Flink CDC
分析侧：Kafka ODS → Flink SQL DWD → Kafka DWD / Doris 明细
        Flink SQL DWS → Doris 汇总 → Doris ADS 视图 → Spring Boot 查询接口 → 实时看板
```

业务系统产生事实，分析链路异步消费，不参与核心事务。

## 三、为什么需要这个技术（原理深入）

整套改造可以按模块拆解，每篇后续文章会深入原理，这里先给全景：

1. **认证链路**（JWT + Redis + ThreadLocal）：登录签发 30 分钟 HS256 accessToken；随机 refreshToken 存 Redis Hash（TTL 7 天）。普通请求只验 JWT 不查 Redis，拦截器把用户放入 ThreadLocal，请求结束统一清理。accessToken 过期后用 refreshToken 续签。→ 见《登录认证：从 Session 到 JWT + Redis 双 Token》
2. **链路追踪**（TraceID + MDC + AOP）：order 0 拦截器读取或生成 TraceID，写入 MDC 与响应头；AOP 环绕通知记录 URI、处理器、成功标志与耗时，异常继续抛出。→ 见《请求链路追踪：TraceID + MDC + AOP 接口耗时埋点》
3. **二级缓存**（Caffeine + Redis）：查询顺序 Caffeine → Redis → MySQL，命中下层向上回填；L1 最多 1 万条、30 秒过期，L2 正常 30 分钟、空值 2 秒防穿透；更新后删 L2、Pub/Sub 通知各实例清 L1。→ 见《商户缓存治理：穿透、击穿、雪崩与二级缓存》
4. **业务 ID 生成**（雪花思想 + Redis 自增）：时间戳左移 32 位或上当日自增序列，生成全局唯一、趋势递增的订单 ID，避免依赖数据库自增主键。→ 见《业务 ID 生成：为什么不用数据库自增》
5. **秒杀链路**（Lua + Redisson + 异步队列）：Redis Lua 原子校验库存与一人一单并预扣 → 写入本地有界队列 → 单线程消费者加用户维度 Redisson 锁 → Spring 代理执行事务：条件扣库存（`stock > 0`）防超卖，唯一索引防重复。→ 见《优惠券秒杀：从超卖问题到 Lua + Redisson + 异步削峰》
6. **社交通知**（RabbitMQ）：点赞、评论、关注在事务提交后（`afterCommit`）投递 durable direct exchange，消费者落库通知表，支持未读数与已读。→ 见《社交模块：Feed 流与 RabbitMQ 异步通知》
7. **实时数仓**（Kafka + Flink + Doris）：行为事件写 Kafka，订单与券主数据走 Flink CDC；Flink SQL 做校验、按 eventId 去重、脏数据分流和自然日聚合，写入 Doris Unique Key 表，ADS 视图供看板查询。→ 见《实时数仓：Kafka + Flink + Doris 行为事件链路》与《实时数仓压测与故障恢复》

## 四、不用这个技术怎么办（替代方案与当前边界）

每一篇都会有详细的替代方案讨论，这里先给总的原则：

- **不用 JWT**：可以回退到 Session + Redis 共享存储，代价是每次请求都要访问 Redis 查登录态，且集群下仍有运维成本。
- **不用 Redis**：全部直查 MySQL，热点数据下数据库扛不住；也没有分布式锁和计数器的实现基础。
- **不用 MQ**：社交通知可以同步写库，但主链路变长、耦合升高；秒杀削峰可以用 Redis Stream 替代本地队列。
- **不用 Flink/Doris**：可以在 MySQL 上做定时聚合，但实时性差、聚合 SQL 会干扰 OLTP。

**当前边界（必须说清楚）**：这是一个**个人学习项目**，所有功能都在本地单机 / Docker Compose 环境验证，不是生产系统。具体包括：

- 秒杀当前使用 JVM 本地阻塞队列做削峰，**不是** RabbitMQ；没有可靠队列、失败重试、Redis 补偿和订单状态查询闭环。
- RabbitMQ 目前没有 publisher confirm、消费幂等、重试队列和死信队列。
- TraceID 是**单体 HTTP 请求级**链路日志，不是完整分布式追踪（没有 Span、跨服务采样）。
- 实时数仓是单 Broker、单 TaskManager、单 FE/BE 的演示环境；压测数据（约 986 events/s、P95 上界 21.93 秒等）只在固定环境实测，不能外推为生产容量。
- 登录验证码只生成并写 Redis 输出日志，没有接入真实短信服务。

## 小结

- 这是一个在课程项目之上持续改造的个人学习项目，目标是把每个设计决策讲清楚。
- 覆盖六大方向：认证、链路追踪、缓存治理、高并发秒杀、异步解耦、实时数仓。
- 业务系统与分析系统解耦：业务产生事实，分析链路异步消费。
- 所有结论都保持诚实口径：本地验证的结论不冒充生产能力。
