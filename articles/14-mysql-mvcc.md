# MySQL MVCC：版本链、ReadView 与隔离级别的实现

> 摘要：MVCC（多版本并发控制）让"读不加锁"成为可能——同一行数据在逻辑上存在多个版本，快照读沿版本链找到自己可见的那一个，从而在不阻塞写的情况下保证读一致性。本文讲清 MVCC 的底层三件套（隐藏字段、undo 版本链、ReadView），区分快照读与当前读，最后用中文隔离级别表把"读已提交 vs 可重复读"的差别讲透——并说明 MySQL 的可重复读为什么能额外防住幻读。

## 一、为什么要这样做（业务背景与痛点）

数据库并发场景下，读和写会互相干扰。最朴素的方案是"读写都加锁"：读锁和写锁互斥，一个事务在写，其他事务的读全部阻塞——并发度极低。另一个极端是"读不加锁"，但会读到别的事务**未提交**的中间数据（脏读）。

MVCC 的目标是：**读不加锁、不阻塞写，同时读到的数据是一致的**。实现思路是"多版本"——不覆盖旧值，而是把旧版本保留下来（通过 undo log），每个读事务根据自己的"视角"（ReadView）看到合适的版本。这样写事务继续改最新版本，读事务看自己该看的版本，互不阻塞。

本项目里最典型的场景：秒杀 `count()` 一人一单判断、Feed 列表读取，都是快照读——它们在事务里看到的是"一致快照"，不会因为别人并发插入而跳动。

## 二、用什么方法解决（方案对比）

并发控制的两条路线：

| 方案 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **悲观锁**（全加锁） | 读写都加锁，互斥执行 | 实现简单、绝对正确 | 并发度极低，读也被阻塞 |
| **MVCC + 乐观读** | 读走版本链不加锁，写走锁 | 读不阻塞写，并发度高 | 机制复杂，写仍需锁/唯一约束兜底 |

InnoDB 是两者的结合：**快照读走 MVCC（不加锁），当前读走锁（行锁/间隙锁）**。读一致性靠 MVCC，写互斥靠锁，各管一段。

## 三、为什么需要这个技术（原理深入）

### 3.1 三件套之一：隐藏字段（不是"版本号字段"）

每行数据除业务列外还有隐藏列（`SELECT *` 看不到）：

- **DB_TRX_ID**：最近一次修改这行的事务 ID；
- **DB_ROLL_PTR**：回滚指针，指向 undo log 里的旧版本；
- **DB_ROW_ID**：无主键时隐藏生成的行 ID（有主键则不用）。

注意：**InnoDB 没有显式的版本号字段**。"版本"由 DB_TRX_ID（谁改的）+ DB_ROLL_PTR（改之前长什么样）共同表达——这就是很多人记忆里"MVCC 有个版本字段"的真相，只是它由两个隐藏列承载。

### 3.2 三件套之二：undo 版本链

每次 UPDATE，旧版本写入 undo log，新行数据的 DB_ROLL_PTR 指向它，DB_TRX_ID 更新为当前事务 ID。于是同一行形成单向版本链：

```
当前版本 v3 ──DB_ROLL_PTR──▶ 旧版本 v2 ──DB_ROLL_PTR──▶ 旧版本 v1
DB_TRX_ID=T3                DB_TRX_ID=T2                DB_TRX_ID=T1
```

最新版本存在聚簇索引数据页里，旧版本存在 undo log 里。读当前值直接读数据页；读历史版本沿指针往 undo 里找。

### 3.3 三件套之三：ReadView（读视图）

快照读触发时生成 ReadView，包含 4 个关键信息：

```
m_ids         创建 ReadView 时还在活跃（未提交）的事务 ID 列表
min_trx_id    m_ids 中最小的 ID
max_trx_id    下一个将分配的事务 ID（m_ids 最大值 + 1）
creator_trx_id 当前事务自己的 ID
```

可见性判断（对版本链上每个版本的 DB_TRX_ID 依次判断，从最新往回找）：

| 条件 | 结论 |
|---|---|
| DB_TRX_ID < min_trx_id | ✅ 可见（ReadView 创建前已提交） |
| DB_TRX_ID >= max_trx_id | ❌ 不可见（未来事务） |
| DB_TRX_ID ∈ m_ids | ❌ 不可见（活跃未提交事务） |
| DB_TRX_ID == creator_trx_id | ✅ 可见（自己改的） |
| 其他 | 沿 DB_ROLL_PTR 找上一个版本重新判断 |

### 3.4 快照读 vs 当前读（MVCC 的分界线）

| 读类型 | 语句 | 机制 |
|---|---|---|
| **快照读** | 普通 SELECT（不加锁） | ReadView + 版本链，不加锁，读历史版本 |
| **当前读** | SELECT ... FOR UPDATE / UPDATE / DELETE / INSERT | 读最新版本 + 加锁（行锁/间隙锁） |

写操作必须基于最新数据，所以 UPDATE/DELETE 总是当前读（读最新 + 加锁）。本项目里：`count()` 是快照读；`UPDATE ... SET stock=stock-1 WHERE stock>0` 是当前读——它靠锁 + 条件保证原子，不靠 MVCC。

### 3.5 中文隔离级别表：差别就在"ReadView 换不换"

| 隔离级别 | 英文 | 读类型 | 怎么实现 |
|---|---|---|---|
| 读未提交 | READ UNCOMMITTED | 直接读最新版 | 不用 MVCC（会脏读） |
| 读已提交 | READ COMMITTED | 快照读 | **每次 SELECT 生成新 ReadView** → 能读到别的事务刚提交的 → 不可重复读 |
| 可重复读 | REPEATABLE READ | 快照读 | **第一次 SELECT 生成 ReadView 整个事务复用** → 事务内永远看到同一快照 → 可重复读（MySQL 默认） |
| 串行化 | SERIALIZABLE | 全变当前读 | 所有读加锁，靠锁实现，性能最差 |

**核心差别一句话**：读已提交每次 SELECT 换 ReadView，可重复读只生成一次 ReadView。

### 3.6 并发问题对照

| 并发问题 | 定义 | 防住的级别 |
|---|---|---|
| 脏读 | 读到未提交数据 | 读已提交起防住 |
| 不可重复读 | 同事务内同一行两次读不同 | 可重复读起防住 |
| 幻读 | 同事务内同一条件两次查出不同行数 | MySQL 可重复读防住（ReadView 复用 + 间隙锁） |

**MySQL 可重复读为什么能防幻读**（其他数据库的 RR 不能）：
1. 快照读：ReadView 只生成一次，新插入的行不在快照里，读不到；
2. 当前读：间隙锁 / next-key lock 锁住范围，别的事务插不进这个区间。

## 四、不用这个技术怎么办（替代方案与当前边界）

- **不用 MVCC 全用锁**：读也被写阻塞，并发度崩盘，秒杀场景的读吞吐会变成灾难；
- **不用 ReadView 只用锁**：回到读已提交的"每次读最新已提交"，同一事务内数据不一致（不可重复读），报表类逻辑会错乱；
- **读一致性与写互斥混为一谈**：很多人以为"MVCC 能防重复下单"——不对，MVCC 保证的是读一致性，**写互斥要靠锁 + 唯一索引**。

**本项目中的边界**：秒杀 `count()` 判断一人一单是快照读，两个并发事务各自看到"还没有订单"，所以防重复必须靠 `uk_user_voucher` 唯一索引硬兜底（详见秒杀篇）——MVCC 管"看到什么"，锁和唯一约束管"谁能改"，两者缺一不可。

**生产建议**：报表/统计类长事务注意隔离级别选择（读已提交更适合长事务，可重复读快照会占用 undo 版本保留时间）；写入密集场景把事务缩短，减少 undo 版本链长度和锁持有时间。

## 小结

1. MVCC 三件套：隐藏字段（DB_TRX_ID + DB_ROLL_PTR）、undo 版本链、ReadView——没有显式"版本号字段"。
2. 快照读走 MVCC 不加锁，当前读（UPDATE/DELETE/FOR UPDATE）读最新 + 加锁。
3. 读已提交每次 SELECT 换 ReadView；可重复读只生成一次——这是两种隔离级别读语义差异的根源。
4. MySQL 可重复读靠"ReadView 复用 + 间隙锁"额外防住幻读（其他数据库的 RR 做不到）。
5. MVCC 保证读一致性，不保证写互斥；防重复下单最终靠唯一索引等硬约束。
6. 隔离级别从低到高：脏读 → 不可重复读 → 幻读依次被解决，代价是并发度下降。
