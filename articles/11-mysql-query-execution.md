# MySQL 一条查询语句的执行流程：从连接器到存储引擎（含 JOIN 复杂度）

> 摘要：一条 SQL 在 MySQL 里要经过连接器、分析器、优化器、执行器，最后才到存储引擎真正读写数据。理解这个骨架，才能明白"为什么加了索引就快""为什么 JOIN 有时慢如蜗牛"。本文以秒杀订单表的一条真实查询为例，走完五步流程，再展开 INNER JOIN 的四种执行算法与复杂度分析，最后给出用 EXPLAIN 定位性能问题的实操方法。这是 MySQL 系列的第一篇，后续索引、日志、MVCC 都建立在这个骨架上。

## 一、为什么要这样做（业务背景与痛点）

MySQL 是一个成熟的关系型数据库，但它不是一个"黑盒"：一条 SQL 最终的执行效果，取决于它经过了哪些阶段、每个阶段做了什么决定。如果只知道"写了 SQL 就能查到数据"，遇到下面这些问题是无法回答的：

- 同样的 SQL，为什么有的表秒回、有的表跑半天？
- 为什么加了索引还是全表扫描？
- 为什么两个表 JOIN 一下，数据量不大却慢得离谱？
- EXPLAIN 出来的 `type`、`rows`、`key_len` 到底意味着什么？

不搞清楚执行流程，排查性能问题时只能盲试：加索引试试、改 SQL 试试。理解了骨架之后，所有优化手段都变成了"我能看到它卡在哪个阶段、为什么卡"，排查就有了方向。

## 二、用什么方法解决（方案对比）

MySQL 的架构可以拆成两层：

- **Server 层**：连接管理、SQL 解析、优化、执行调度——对所有存储引擎通用；
- **存储引擎层**：真正读写磁盘数据的组件，InnoDB 是默认引擎（支持事务、行锁、崩溃恢复），MyISAM 是历史遗留（表锁、无事务）。

一条查询的处理，就是 Server 层负责"指挥"，InnoDB 负责"干活"。整条链路分五步：

```
客户端 → 连接器（鉴权） → 分析器（词法/语法） → 优化器（选执行计划）
       → 执行器（调引擎接口） → InnoDB（索引查找、读数据页）
```

## 三、为什么需要这个技术（原理深入）

以秒杀订单表的真实查询为例：

```sql
SELECT * FROM tb_voucher_order WHERE user_id = 12345 AND voucher_id = 100;
```

### 第 1 步：连接器

建立连接、校验用户名密码，**权限判断在此完成**。连接建立时就确定了这个连接能干什么；之后权限变了，已建立的连接不受影响（要重连才生效）。`wait_timeout`（默认 8 小时）后服务端会断开空闲连接。项目里的连接池（HikariCP/Druid）本质就是复用这些连接，减少握手开销。

### 第 2 步：分析器

词法分析把 SQL 拆成"单词"（SELECT、user_id、12345），语法分析检查语法是否正确。这一步纯文本处理，**不接触磁盘**。

### 第 3 步：优化器（最关键）

决定"怎么执行最快"。包括选哪条索引、join 时先查哪张表等。成本模型基于统计信息估算行数。上面这条查询，优化器大概率选 `uk_user_voucher (user_id, voucher_id)` 唯一索引，因为它是"等值 + 覆盖"，成本最低——这就是为什么复合索引的字段顺序要匹配查询条件。

### 第 4 步：执行器

真正开始执行，调用存储引擎接口。执行前会再校验一次表级权限。按执行计划调用 InnoDB 的 `index_read`/`index_scan` 等接口，逐行返回给 Server 层做剩余处理（排序、LIMIT、函数计算等）。

### 第 5 步：存储引擎（InnoDB）

真正的数据读写。走二级索引 `uk_user_voucher` 定位叶子节点，叶子里存的是 `(user_id, voucher_id, 主键id)`——因为查询恰好只用了索引里的列（此处为覆盖场景，不需要回表），一次索引查找即可返回。

### 附：INNER JOIN 的复杂度怎么分析

JOIN 在 MySQL 里没有独立算子，本质是"嵌套循环"的变体，复杂度取决于**连接条件有没有索引**：

| 算法 | 触发条件 | 复杂度 | 说明 |
|---|---|---|---|
| Index Nested-Loop（INLJ） | 被驱动表连接字段有索引 | O(N·logM) | 驱动表每行去索引树查一次，最优 |
| Block Nested-Loop（BNL） | 被驱动表无索引 | O(N·M) 次比较 | 用内存 Join Buffer 批量比对，减少磁盘 IO |
| Hash Join | 8.0.18+，等值连接 | O(N+M) | 小表建哈希表、大表 O(1) 探测，等值连接时最优 |

分析三步法：① 看连接条件有没有索引（EXPLAIN 里被驱动表 `type` 是 `ref`/`eq_ref` 还是 `ALL`）；② 确定驱动表（优化器按成本选，通常小表驱动大表，EXPLAIN 第一行是驱动表）；③ 代入行数算。

**关键认知**：数据库的瓶颈是磁盘 IO 不是 CPU。INLJ 快在"每次只做 2~4 次索引页读取"；BNL 慢在"要全表扫被驱动表若干次"。所以优化 JOIN 的第一手段永远是**给被驱动表的连接字段建索引**。

## 四、不用这个技术怎么办（替代方案与当前边界）

- **不加索引硬 JOIN**：只能用 BNL 全表比对，数据量一大磁盘 IO 呈乘积增长；
- **业务层避免 JOIN**：把需要的字段**冗余进单表**（用空间换 join）。本项目订单表就是这么做的：`fillOrderSnapshot` 把 shop_id、券面金额等**快照字段**直接存进订单表，业务查询全是单表，完全不写 JOIN；
- **换分析引擎**：真正的多表聚合挪到 Doris/Flink 实时数仓做，MySQL 只承担单表 OLTP——这正是"OLTP/OLAP 分离"思想的落地。

**实操建议**：所有查询优化都用 `EXPLAIN` 验证，重点看 `type`（出现 `ALL` 即全表扫描）、`key`（实际用的索引）、`rows`（估算扫描行数）、`key_len`（用到索引的列数）、`Extra`（Using filesort / Using temporary 需要警惕）。

## 小结

1. 一条 SQL 走五步：连接器（鉴权）→ 分析器（解析）→ 优化器（选计划）→ 执行器（调引擎）→ InnoDB（读数据）。
2. Server 层指挥、存储引擎干活，InnoDB 负责真正读写磁盘。
3. JOIN 复杂度取决于连接条件有没有索引：有索引是 INLJ（O(N·logM)），无索引是 BNL（O(N·M)）或 Hash Join（8.0 等值连接 O(N+M)）。
4. 数据库性能的命门是磁盘 IO：树矮（索引层数少）、扫描少，才是快的本质。
5. 业务层用"快照字段冗余"避免 JOIN、分析场景交给 Doris，是规避 JOIN 复杂度的工程手段。
6. 一切优化以 EXPLAIN 为准，不要凭感觉加索引。
