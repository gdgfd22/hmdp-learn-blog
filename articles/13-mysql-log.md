# MySQL 三大日志：redo log、undo log、binlog 与两阶段提交

> 摘要：MySQL 的可靠性（事务不丢、可回滚、可恢复、可复制）不是靠运气，而是靠三份日志分工协作。redo log 用 WAL 机制保证"已提交事务不丢"；undo log 记录逻辑逆操作，支撑回滚和 MVCC 版本链；binlog 是 Server 层的逻辑日志，负责主从复制和时间点恢复。三者之间还靠"两阶段提交"保证崩溃后主从一致。本文逐个拆解三份日志，最后用本项目秒杀事务串一遍完整生命周期。

## 一、为什么要这样做（业务背景与痛点）

假设没有日志，InnoDB 面临三个无法回答的问题：

1. **持久性**：数据页先改在内存（Buffer Pool），再异步刷回磁盘（随机 IO 太慢，不能每次提交都刷盘）。如果提交后、刷盘前宕机，已提交的数据就丢了——用户下单成功却查不到订单，这是不可接受的；
2. **原子性**：事务执行到一半出错要回滚，怎么撤销已做的修改？扣了库存但订单没插成功，必须把库存加回来；
3. **复制与恢复**：主从同步、误删数据后的时间点恢复，靠什么把"变更"传给从库或重放到指定时刻？

日志就是这三件事的答案。理解日志，才能理解事务 ACID 中的 **A（原子性）和 D（持久性）** 到底靠什么实现。

## 二、用什么方法解决（方案对比）

三份日志各司其职，先给总表：

| 日志 | 归属层 | 记录内容 | 核心作用 | 写入时机 |
|---|---|---|---|---|
| **redo log** | InnoDB 引擎 | **物理变化**（第几页偏移多少改成什么） | 崩溃恢复：已提交事务不丢 | 事务提交时（WAL） |
| **undo log** | InnoDB 引擎 | **逻辑逆操作**（撤销刚才的修改） | 回滚 + MVCC 版本链 | 事务执行过程中 |
| **binlog** | MySQL Server 层 | **逻辑日志**（SQL 或行变更） | 主从复制 + 数据恢复 | 事务提交时 |

关键区分：redo/undo 是 InnoDB 的（只对 InnoDB 有效），binlog 是 Server 层的（所有引擎通用）；redo 记"做了什么"，undo 记"怎么撤销"，binlog 记"最终结果"。

## 三、为什么需要这个技术（原理深入）

### 3.1 redo log：WAL（Write-Ahead Logging）

更新的真实路径是：改内存里的 Buffer Pool 页（快）→ 磁盘页还是旧值（不能每次都刷，随机 IO 慢）。WAL 的解法是：**先顺序写 redo log**（"我要怎么改"的物理日志，顺序 IO 快），事务提交时只要 redo 刷盘成功就算提交完成；数据页可以晚点再异步刷回磁盘。宕机后启动时重放 redo log，把没刷盘的已提交修改恢复出来——**已提交事务绝不丢**。

redo log 是**固定大小、环形写入**的文件组：

```
[已刷盘区域 ← checkpoint | 未刷盘区域（需重放） ← write pos | 空闲]
```

- `write pos`：当前写的位置；`checkpoint`：已刷盘的位置；
- 两者之间就是要靠 redo 恢复的部分；write pos 追上 checkpoint 时必须强制刷盘（redo 满了会阻塞写入）。

刷盘策略 `innodb_flush_log_at_trx_commit`：`1`（默认，每次提交刷盘，最稳）、`0`（每秒刷，最多丢 1 秒）、`2`（写 OS 缓存每秒刷，MySQL 崩溃不丢、OS 崩溃丢）。

### 3.2 undo log：回滚 + MVCC 版本链的原料

undo log 在**事务执行过程中**就写，记录逻辑逆操作：插入 → 记"删除该行"；删除 → 记"恢复该行"；更新 → 记"改回旧值"。

两大作用：
1. **回滚**：事务出错/ROLLBACK 时，按 undo 逆序撤销，回到事务开始前；
2. **MVCC 版本链**：每次修改时旧版本通过 DB_ROLL_PTR 指针链到 undo log，形成版本链。快照读时沿链找"当前事务可见"的版本（详见 MVCC 篇）。undo 不是无限保留，快照释放后由 purge 线程清理。

### 3.3 binlog：Server 层的逻辑日志

记录"事务最终对数据做了哪些变更"，两种格式：STATEMENT（原始 SQL，体积小但 NOW() 等不确定函数重放不一致）、ROW（行变更前后快照，最可靠，8.0 默认）、MIXED（混合）。

两大作用：
1. **主从复制**：主库写 binlog → 从库 IO 线程拉取到 relay log → SQL 线程重放；
2. **数据恢复**：全量备份 + binlog 增量重放到误操作前的时间点（`mysqlbinlog --stop-datetime`）。

### 3.4 两阶段提交：redo 和 binlog 保持一致

redo（InnoDB）和 binlog（Server）是**两份独立的日志**，崩溃时若不一致，主从数据就对不上（主库有、从库没有，或反之）。解法是把提交拆成两阶段：

```
阶段1（prepare）：写 redo log 标记 prepare → 刷盘
阶段2（commit）：写 binlog → 刷盘 → 把 redo log 标记为 commit
```

崩溃恢复时的裁决规则：

| 崩溃时刻 | 状态 | 恢复动作 |
|---|---|---|
| 写完 redo(prepare)、binlog 没写 | prepare | **回滚**（binlog 里没有它，从库也没有，主库不能有） |
| 写完 binlog、redo 仍 prepare | prepare 但 binlog 完整 | **提交**（binlog 已记录，重放它让从库一致） |
| redo 已是 commit | commit | 直接生效 |

**一句话：以 binlog 是否完整写入为"事务是否生效"的裁决依据**——binlog 在就提交、不在就回滚，崩溃后主从永远一致。

## 四、不用这个技术怎么办（替代方案与当前边界）

- **不用 WAL**：每次提交都直接刷数据页到磁盘，事务提交慢到无法接受（随机 IO）；
- **不用 undo**：事务无法回滚，也无法实现 MVCC 快照读，只能全表加锁读；
- **不用 binlog**：没有主从复制、无法做时间点恢复，一次误删就是灾难。

**本项目中的完整生命周期**：秒杀 `@Transactional` 事务（`createVoucherOrder2`）背后，一次下单事务完整走一遍——执行 INSERT/UPDATE 改 Buffer Pool + 写 undo log → 提交时写 redo（prepare）→ 写 binlog → 标记 commit → 之后异步刷脏页。中途出错用 undo 回滚；MySQL 崩溃用 redo 恢复已提交事务、用 undo 回滚未提交事务。这也是"扣库存成功、插订单失败会怎样"的答案：`@Transactional` 把两步包进同一事务，任何一步抛异常，undo 会把库存扣减和订单插入一起回滚。

**当前边界**：本地单机环境没有配置主从，binlog 的复制能力未被使用；日志相关参数（`innodb_flush_log_at_trx_commit` 等）保持默认。面试时应说明"理解原理，但生产级复制与高可用配置尚未在项目中落地"。

## 小结

1. redo log：物理日志 + WAL，先顺序写日志再刷数据页，保证**已提交不丢**（持久性），环形结构 + checkpoint 控制。
2. undo log：逻辑逆操作，事务执行时写，支撑**回滚**（原子性）与 **MVCC 版本链**。
3. binlog：Server 层逻辑日志，负责**主从复制**与**时间点恢复**，STATEMENT/ROW/MIXED 三种格式。
4. 两阶段提交让 redo 与 binlog 一致：binlog 在就提交、不在就回滚，崩溃后主从一致。
5. 三份日志 + 锁共同构成事务 ACID：原子性靠 undo、持久性靠 redo、隔离性靠锁 + MVCC。
6. 本项目的事务回滚（扣库存 + 插订单一起撤销）就是 undo log 在真实业务里的体现。
