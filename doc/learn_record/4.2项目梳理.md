首先我们在宏观上先有一个认知：

前面在讲解HTTP协议的时候，我们提到HTTP协议是无状态协议。什么又是无状态的协议？

所谓无状态，指的是每一次请求都是独立的，下一次请求并不会携带上一次请求的数据。而浏览器与服务器之间进行交互，基于HTTP协议也就意味着现在我们通过浏览器来访问了登陆这个接口，实现了登陆的操作，接下来我们在执行其他业务操作时，服务器也并不知道这个员工到底登陆了没有。因为HTTP协议是无状态的，两次请求之间是独立的，所以是无法判断这个员工到底登陆了没有。

那应该怎么来实现登录校验的操作呢？具体的实现思路可以分为两部分：

1. 在员工登录成功后，需要将用户登录成功的信息存起来，记录用户已经登录成功的标记。

2. 在浏览器发起请求时，需要在服务端进行统一拦截，拦截后进行登录校验。

   

我们要完成以上操作，会涉及到web开发中的两个技术：

1. 会话技术：用户登录成功之后，在后续的每一次请求中，都可以获取到该标记。

   Cookie,存储在客户端浏览器的。**优缺点：**

   - 优点：HTTP协议中支持的技术（像Set-Cookie 响应头的解析以及 Cookie 请求头数据的携带，都是浏览器自动进行的，是无需我们手动操作的）
   - 缺点：
     - 移动端APP(Android、IOS)中无法使用Cookie
     - 不安全，用户可以自己禁用Cookie
     - Cookie不能跨域

   Session,它是服务器端会话跟踪技术,**优缺点**

   - 优点：Session是存储在服务端的，安全
   - 缺点：
     - 服务器集群环境下无法直接使用Session
     - 移动端APP(Android、IOS)中无法使用Cookie
     - 用户可以自己禁用Cookie
     - Cookie不能跨域

   JWT令牌:本质就是一个字符串

   - 优点：
     - 支持PC端、移动端
     - 解决集群环境下的认证问题
     - 减轻服务器的存储压力（无需在服务器端存储）
   - 缺点：需要自己实现（包括令牌的生成、令牌的传递、令牌的校验）

2. 统一拦截技术：过滤器Filter、拦截器Interceptor

### session实现登录流程-缺点

每个tomcat中都有一份属于自己的session,假设用户第一次访问第一台tomcat，并且把自己的信息存放到第一台服务器的session中，但是第二次这个用户访问到了第二台tomcat，那么在第二台服务器上，肯定没有第一台服务器存放的session，所以此时 整个登录拦截功能就会出现问题，我们能如何解决这个问题呢？早期的方案是session拷贝，就是说虽然每个tomcat上都有不同的session，但是每当任意一台服务器的session修改时，都会同步给其他的Tomcat服务器的session，这样的话，就可以实现session的共享了

但是这种方案具有两个大问题

1、每台服务器中都有完整的一份session数据，服务器压力过大。

2、session拷贝数据时，可能会出现延迟

所以咱们后来采用的方案都是基于redis来完成，我们把session换成redis，redis数据本身就是共享的，就可以避免session共享的问题了

### 三：redis替代session

当注册完成后，用户去登录会去校验用户提交的手机号和验证码，是否一致，如果一致，则根据手机号查询用户信息，不存在则新建，最后将用户数据保存到redis，并且生成token作为redis的key，当我们校验用户是否登录时，会去携带着token进行访问，从redis中取出token对应的value，判断是否存在这个数据，如果没有则拦截，如果存在则将其保存到threadLocal中，并且放行。

```
@Override
public Result login(LoginFormDTO loginForm, HttpSession session) {
    // 1.校验手机号
    String phone = loginForm.getPhone();
    if (RegexUtils.isPhoneInvalid(phone)) {
        // 2.如果不符合，返回错误信息
        return Result.fail("手机号格式错误！");
    }
    // 3.从redis获取验证码并校验
    String cacheCode = stringRedisTemplate.opsForValue().get(LOGIN_CODE_KEY + phone);
    String code = loginForm.getCode();
    if (cacheCode == null || !cacheCode.equals(code)) {
        // 不一致，报错
        return Result.fail("验证码错误");
    }

    // 4.一致，根据手机号查询用户 select * from tb_user where phone = ?
    User user = query().eq("phone", phone).one();

    // 5.判断用户是否存在
    if (user == null) {
        // 6.不存在，创建新用户并保存
        user = createUserWithPhone(phone);
    }

    // 7.保存用户信息到 redis中
    // 7.1.随机生成token，作为登录令牌
    String token = UUID.randomUUID().toString(true);
    // 7.2.将User对象转为HashMap存储
    UserDTO userDTO = BeanUtil.copyProperties(user, UserDTO.class);
    Map<String, Object> userMap = BeanUtil.beanToMap(userDTO, new HashMap<>(),
            CopyOptions.create()
                    .setIgnoreNullValue(true)
                    .setFieldValueEditor((fieldName, fieldValue) -> fieldValue.toString()));
    // 7.3.存储
    String tokenKey = LOGIN_USER_KEY + token;
    stringRedisTemplate.opsForHash().putAll(tokenKey, userMap);
    // 7.4.设置token有效期
    stringRedisTemplate.expire(tokenKey, LOGIN_USER_TTL, TimeUnit.MINUTES);

    // 8.返回token
    return Result.ok(token);
}
```

## 现在方案：

### 使用 ***\*JWT\**** 完成身份验证，结合Redis实现会话管理，并自定义拦截器配合***\*ThreadLocal\****实时校验并在请求链路内***\*共享用户信息\****。

- 使用 JWT accessToken 做身份认证
- 使用 Redis 存 refreshToken，做会话管理
- 自定义拦截器解析 Authorization 里的 JWT
- 解析成功后把用户信息放进 ThreadLocal
- 业务代码通过 UserHolder 取当前用户

## 问题1：拦截器的流程

在你这个 JWT + Redis 方案里，拦截器流程可以理解成两层：

1. `JwtTokenInterceptor`
2. `LoginInterceptor`

先看顺序，在 [MvcConfig.java](/E:/Java_learn/heimadianping/hm-dianping/src/main/java/com/hmdp/config/MvcConfig.java) 里是先注册 JWT 拦截器，再注册登录拦截器。

完整流程是这样的：

1. 前端发请求  
请求头里带：
```http
Authorization: Bearer accessToken
```

2. 先进入 `JwtTokenInterceptor`  
代码在 [JwtTokenInterceptor.java](/E:/Java_learn/heimadianping/hm-dianping/src/main/java/com/hmdp/Interceptor/JwtTokenInterceptor.java)

它会做几件事：

- 取请求头里的 `authorization`
- 去掉 `Bearer ` 前缀
- 调 [JwtTool.java](/E:/Java_learn/heimadianping/hm-dianping/src/main/java/com/hmdp/utils/JwtTool.java) 验签和解析 JWT
- 如果 token 合法，就拿到 `UserDTO`
- 把 `UserDTO` 放进 `ThreadLocal`，也就是 [UserHolder.java](/E:/Java_learn/heimadianping/hm-dianping/src/main/java/com/hmdp/utils/UserHolder.java)

这一层的目标不是拦人，而是“尽量解析用户”。

也就是说：

- 没 token，直接放行
- token 无效，也先放行
- token 有效，就把用户塞进 `UserHolder`

3. 再进入 `LoginInterceptor`  
代码在 [LoginInterceptor.java](/E:/Java_learn/heimadianping/hm-dianping/src/main/java/com/hmdp/Interceptor/LoginInterceptor.java)

它只做一件事：

- 看 `UserHolder.getUser()` 有没有值

如果没有，说明当前请求没登录：
- 返回 `401`
- 拦截结束

如果有，说明 JWT 已经解析成功：
- 放行到 Controller / Service

4. 业务代码里取当前用户  
到 Controller 或 Service 后，就不用再自己解析 token 了，直接：

```java
UserDTO user = UserHolder.getUser();
```

比如你项目里很多地方就是这么干的。

5. 请求结束后清理 `ThreadLocal`  
在 `JwtTokenInterceptor.afterCompletion()` 里会调用：

```java
UserHolder.removeUser();
```

避免线程复用导致用户串数据。

你可以把它记成一句话：

- `JwtTokenInterceptor` 负责“认人”
- `LoginInterceptor` 负责“拦未登录的人”
- `UserHolder` 负责“在一次请求里共享当前用户”

如果画成简图，就是：

```text
请求进来
-> JwtTokenInterceptor 解析 JWT
-> 成功则 UserHolder.saveUser(user)
-> LoginInterceptor 检查 UserHolder 是否有用户
-> 有则放行到业务代码
-> 业务代码中 UserHolder.getUser()
-> 请求结束 UserHolder.removeUser()
```

再补一个你这套里和 Redis 的关系：

- 普通接口校验时，拦截器主要看的是 `JWT`
- Redis 主要管的是 `refreshToken` 会话
- 所以“访问接口”靠 JWT
- “续登录、退出登录”靠 Redis

## 问题二：怎么配合ThreadLocal的，UserHolder

对，核心就是线程。

`UserHolder` 本质上是对 `ThreadLocal` 的一层封装，目的就是：

- 在一次请求处理过程中保存当前登录用户
- 让后面的 Controller、Service、Mapper 相关逻辑都能方便拿到这个用户
- 不用层层传 `userId`

你项目里的 [UserHolder.java](/E:/Java_learn/heimadianping/hm-dianping/src/main/java/com/hmdp/utils/UserHolder.java) 就是这个作用。

为什么和线程有关？

**因为在 Spring MVC 里，一次 HTTP 请求通常由一个线程处理。  所以可以利用 `ThreadLocal` 做“当前请求线程私有的数据存储”。**

流程是：

1. 请求进来
2. 拦截器解析 token，拿到当前用户
3. `UserHolder.saveUser(user)`
4. 后续这个请求里的代码，运行在同一个线程里
5. 任意位置都能 `UserHolder.getUser()`
6. 请求结束后 `UserHolder.removeUser()`

这样你在业务代码里就能直接写：

```java
Long userId = UserHolder.getUser().getId();
```

而不用这样层层传：

```java
controller -> service -> service2 -> dao
```

每一层都加一个 `userId` 参数，会很麻烦。

### 为什么不用全局变量？

因为全局变量会被所有请求共享，线程不安全。  
A 用户请求进来刚存进去，B 用户请求可能马上把它覆盖掉，用户数据就串了。

为什么 `ThreadLocal` 可以？

因为它是“线程隔离”的：

- 线程 A 只能看到自己的 user
- 线程 B 只能看到自己的 user
- 서로不会串

但一定要 `removeUser()`，为什么？

因为 Web 容器线程是复用的，不是请求结束就销毁。  
如果你不清理，下一个请求复用这个线程时，可能会拿到上一个用户的数据，造成严重串号。

所以你这套标准流程就是：

- 拦截器里 `saveUser`
- 业务里 `getUser`
- 请求结束 `removeUser`

一句话理解：

`UserHolder` 就是为了把“当前请求对应的登录用户”安全地绑定到“当前处理请求的线程”上，方便整个请求链路共享。  

### Threadlocal

- ThreadLocal 并不是一个Thread，而是Thread的局部变量。
- ThreadLocal为每个线程提供一份单独的存储空间，具有线程隔离的效果，不同的线程之间不会相互干扰。
- ![image-20260403101336929](C:\Users\Administrator\Nutstore\1\我的坚果云\科研项目工作记录\面试八股\Redis-黑马点评\image-20260403101336929.png)

ThreadLocal 并不是 Thread 的局部变量，这是一个非常经典的易混淆点，恰恰相反 ——Thread 持有自己的 ThreadLocalMap 局部变量，而 ThreadLocal 是操作这个局部变量的「全局工具类」

在同一个线程/同一个请求中，进行数据共享就可以使用 ThreadLocal。

## 背景：MDC

`MDC` 是日志领域里一个非常实用的概念，全称是 **Mapped Diagnostic Context（映射诊断上下文）**，属于日志框架（比如 SLF4J）提供的一种**线程级上下文存储机制**。

你提到的：

```java
import org.slf4j.MDC;
```

就是在用 SLF4J 的 MDC 功能。

------

### 一、简单理解（核心一句话）

👉 **MDC = 给当前线程的日志“打标签”**

你可以往 MDC 里放一些 key-value，比如：

- 用户ID
- 请求ID（traceId）
- IP地址

之后在日志里自动带上这些信息，而不用每次手动拼接。

------

### 二、为什么需要 MDC？

在服务端开发中（尤其是：

- 多线程
- Web 请求
- 微服务

场景下）

日志很容易变成这样：

```
用户A的请求日志
用户B的请求日志
用户A的后续日志
用户C的日志
```

👉 很乱，难以追踪一条完整链路。

------

### 三、MDC 的作用

MDC 可以帮你做到：

✔ 自动在日志中加入上下文信息
✔ 实现“请求级别”的日志追踪
✔ 常用于 traceId / requestId / userId

------

### 四、基本用法

#### 1️⃣ 设置上下文

```java
MDC.put("traceId", "abc123");
MDC.put("userId", "10001");
```

------

#### 2️⃣ 日志打印

```java
log.info("用户发起请求");
```

------

#### 3️⃣ 清理（非常重要！）

```java
MDC.clear();
```

------

### 五、日志输出效果（关键）

你需要在日志配置里加上 MDC 变量，比如（logback）：

```xml
<pattern>
    %d{yyyy-MM-dd HH:mm:ss} [%thread] %-5level %logger - %msg [traceId=%X{traceId}]
</pattern>
```

输出效果：

```
2026-04-02 10:00:00 [http-nio-8080-exec-1] INFO  UserService - 用户发起请求 [traceId=abc123]
```

------

#### 六、底层原理（你这个水平建议理解）

👉 MDC 本质是基于：

```
ThreadLocal<Map<String, String>>
```

也就是说：

| 特性     | 说明                         |
| -------- | ---------------------------- |
| 线程隔离 | 每个线程有自己的 MDC         |
| 自动传递 | 同线程内日志自动带上         |
| 不跨线程 | 新线程不会继承（除非手动传） |

------

### 七、常见使用场景

#### 1️⃣ Web 请求链路追踪（最常见）

```java
String traceId = UUID.randomUUID().toString();
MDC.put("traceId", traceId);
```

👉 每个请求一个 traceId

------

#### 2️⃣ 分布式系统（配合链路追踪）

类似：

- traceId
- spanId

------

#### 3️⃣ 用户行为日志

```java
MDC.put("userId", loginUser.getId());
```

------

### 八、注意事项（非常重要）

#### ❗1. 一定要清理 MDC

```java
try {
    MDC.put("traceId", traceId);
    // 业务逻辑
} finally {
    MDC.clear();
}
```

否则：
👉 **线程复用（线程池）会导致脏数据污染！**

------

#### ❗2. 线程池问题

新线程不会自动继承 MDC：

解决方案：

- 手动传递
- 或使用框架（如 Spring 的 `TaskDecorator`）

------

### 九、一句话总结

👉 **MDC = 给日志自动加“上下文标签”，用于链路追踪和问题排查**

# 一：JWT + Redis 会话管理与 ThreadLocal 用户上下文共享

## 背景

传统 Session 方案虽然实现简单，但在前后端分离、多实例部署场景下扩展性不足，因此项目中采用了 `JWT + Redis` 的认证方案。

其中：

- `accessToken` 负责接口访问认证
- `refreshToken` 存储在 Redis 中，负责会话续期与退出登录控制

## 实现思路

整体登录链路如下：

1. 用户登录成功后，后端签发 `accessToken`
2. 同时生成 `refreshToken` 并写入 Redis
3. 前端本地同时保存 `accessToken + refreshToken`
4. 请求进入后，拦截器解析 JWT
5. 解析成功后将用户信息写入 `ThreadLocal`
6. 业务代码通过 `UserHolder` 获取当前登录用户

# 二：通过 AOP 实现接口访问耗时日志埋点，结合 MDC 和 TraceID 实现请求全链路追踪

## 背景

在 Web 项目中，请求链路较长，请求经过拦截器、Controller、Service、DAO 多层调用后，如果没有统一的链路标识和日志规范，排查问题会比较困难。

因此项目中引入：

- `TraceID` 标识一次请求
- `MDC` 保存线程级日志上下文
- `AOP` 对接口耗时进行统一埋点

从而实现请求级别的日志追踪。

## 实现思路

整体流程如下：

1. 请求进入时，优先从请求头中获取 `X-Trace-Id`
2. 如果没有，则后端自动生成一个新的 `traceId`
3. 将 `traceId` 写入 `MDC`
4. 同时把 `traceId` 回写到响应头，方便前后端联调
5. 通过 AOP 统一拦截 Controller 层接口，记录请求方法、请求路径、处理方法、是否成功以及执行耗时
6. 请求结束后清理 `MDC`，避免线程复用导致脏数据污染

## 核心实现代码

```java
        log.error("request failed traceId={}, method={}, uri={}, handler={}, cost={}ms",
```

```java
public class RedisIdWorker {
    private static final long BEGIN_TIMESTAMP = 1640995200L;
    private static final int COUNT_BITS = 32;

    public long nextId(String keyPrefix) {
        LocalDateTime now = LocalDateTime.now();
        long nowSecond = now.toEpochSecond(ZoneOffset.UTC);

        String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));

                .increment("icr:" + keyPrefix + ":" + date);

        return timestamp << COUNT_BITS | count;
    }
}
```

# 四：商户缓存治理

## 背景

在商户详情查询场景中，数据具有高频读、低频写的特点，因此项目中引入 Redis 作为缓存层，降低数据库访问压力并提升接口响应速度。

## 一：缓存更新策略(Cache Aside ，旁路缓存策略，读多写场景)

读策略：

```
先查 Redis
-> Redis 命中，直接返回
-> Redis 未命中，查 MySQL
-> MySQL 有数据，写入 Redis
-> MySQL 没数据，写入空值防穿透
```

写策略：项目采用的是：

**先更新数据库，再删除缓存。**

见Redis八股

### 问题：不能先删除缓存再更新数据库

在「读+写」并发的时候，会出现缓存和数据库的数据不一致性的问题。

因为先删缓存有并发风险：

```
线程 A 删除缓存 线程 B 查询，发现缓存没了，查旧数据库，写旧缓存 线程 A 更新数据库 最后 Redis 里还是旧数据
```

### 为什么「先更新数据库再删除缓存」不会有数据不一致的问题？

## 二：缓存穿透

#### 什么是缓存穿透？

缓存穿透是大量请求访问的数据，**既不在缓存中，也不在数据库中**，导致数据库的压力骤增。

缓存穿透意味着缓存失去了减轻数据压力的意义，缓存穿透可能有两种原因：

1. **自身业务代码问题**，**业务误操作**导致缓存中的数据和数据库中的数据**都被误删除**了，所以导致缓存和数据库中都没有数据；
2. **黑客恶意攻击**，故意大量访问某些读取不存在数据的业务；

**应对缓存穿透的方案，常见的方案有三种：**

- **第一种方案是限制非法的请求**：当有大量恶意请求访问不存在的数据的时候，也会发生缓存穿透，因此在 API 入口处我们要判断求请求参数是否合理，请求参数是否含有非法值、请求字段是否存在，如果判断出是恶意请求就直接返回错误，避免进一步访问缓存和数据库；对于异常频繁的访问行为，还可以采取黑名单机制，例如将异常 IP 列入黑名单。
- **第二种方案是缓存空值或者默认值**：当我们线上业务发现缓存穿透的现象时，可以针对查询的数据，**将该空结果（如 null 或 {}）缓存起来，并设置一个合理的过期时间**，这样后续请求就可以从缓存中读取到空值或者默认值，返回给应用，而不会继续查询数据库。

- **第三种方案，通过布隆过滤器存储所有可能存在的合法数据的键，当请求到达时，先通过布隆过滤器判断该键是否存在：**
  - 如果布隆过滤器认为该键不存在，直接返回空，不会查询数据库。
  - 如果布隆过滤器认为该键可能存在，则查询缓存和数据库。

项目通过 **缓存空值** 解决缓存穿透，见 [CacheClient.java](/E:/Java_learn/heimadianping/hm-dianping/src/main/java/com/hmdp/utils/CacheClient.java)：


## 三：缓存击穿

如果缓存中的**某个热点数据（被频繁地访问的数据）过期**了，此时大量的请求访问了该热点数据，就无法从缓存中读取，直接访问数据库，数据库很容易就被高并发的请求冲垮，这就是**缓存击穿**的问题。**可以发现缓存击穿跟缓存雪崩很相似，你可以认为缓存击穿是缓存雪崩的一个子集。**

### 1. 互斥锁方案

当缓存未命中时，先尝试获取互斥锁。只有拿到锁的线程去查询数据库并重建缓存，其他线程可以短暂等待后重试读取缓存，或者直接返回默认值。这样可以避免大量请求同时打到数据库。

你的项目里有这种实现：

```
stringRedisTemplate.opsForValue().setIfAbsent(key, "1", 10, TimeUnit.SECONDS); 
```

也就是 Redis 的 SET NX EX 思路。

```java

        Thread.sleep(50);
        return queryWithMutex(keyPrefix, id, type, dbFallback, time, unit);
    }
    ...
}
```

### 2. 逻辑过期方案

**逻辑过期**
热点数据不依赖 Redis 的物理过期时间，而是在缓存 value 里存一个逻辑过期时间。查询时如果发现逻辑过期，先返回旧数据，同时尝试加锁并开启后台线程重建缓存。

这种方案的好处是：

- 用户请求不会阻塞太久
- 热点 key 不会突然消失
- 可用性更好

缺点是：

- 可能短暂返回旧数据
- 适合一致性要求不高的热点数据

```java
    public <R, ID> R queryWithLogicalExpire(
            String keyPrefix, ID id, Class<R> type, Function<ID, R> dbFallback, Long time, TimeUnit unit) {
        String key = keyPrefix + id;
        // 1.从redis查询商铺缓存
        String json = stringRedisTemplate.opsForValue().get(key);
        // 2.判断是否存在
        if (StrUtil.isBlank(json)) {
            // 3.存在，直接返回
            return null;
        }
        // 4.命中，需要先把json反序列化为对象
        RedisData redisData = JSONUtil.toBean(json, RedisData.class);
        R r = JSONUtil.toBean((JSONObject) redisData.getData(), type);
        LocalDateTime expireTime = redisData.getExpireTime();
        // 5.判断是否过期
        if(expireTime.isAfter(LocalDateTime.now())) {
            // 5.1.未过期，直接返回店铺信息
            return r;
        }
        // 5.2.已过期，需要缓存重建
        // 6.缓存重建
        // 6.1.获取互斥锁
        String lockKey = LOCK_SHOP_KEY + id;
        boolean isLock = tryLock(lockKey);
        // 6.2.判断是否获取锁成功
        if (isLock){
            // 6.3.成功，开启独立线程，实现缓存重建
            CACHE_REBUILD_EXECUTOR.submit(() -> {
                try {
                    // 查询数据库
                    R newR = dbFallback.apply(id);
                    // 重建缓存
                    this.setWithLogicalExpire(key, newR, time, unit);
                } catch (Exception e) {
                    throw new RuntimeException(e);
                }finally {
                    // 释放锁
                    unlock(lockKey);
                }
            });
        }
        // 6.4.返回过期的商铺信息
        return r;
    }
```

### 7.1----Lua脚本是怎么实现原子性的?

```
Redis 中 Lua 脚本的原子性是因为 Redis 会把整个 Lua 脚本当成一条命令执行，而 Redis 本身处理命令是单线程串行的。脚本执行期间，其他客户端的命令不能插入执行，必须等当前脚本执行完成。因此 Lua 脚本可以把多个 Redis 操作组合成一个原子操作，比如分布式锁释放时，把 `get` 判断和 `del` 删除放在同一个 Lua 脚本里，避免误删其他线程的锁。

不过需要注意，Lua 脚本的原子性不是事务回滚机制。如果脚本中前面的写操作已经执行成功，后面发生错误，Redis 不会自动回滚已经执行的命令。
```

### 如果不用lua脚本，你会怎么做？

```
不用 Lua 脚本的话，要看场景。如果只是单机单 JVM，可以用 synchronized 保证 get + 判断 + delete 的原子性；但是在分布式部署下，每个服务实例都有自己的 JVM 锁，synchronized 无法保证多个实例之间的互斥。

如果还是基于 Redis 实现，可以用 WATCH + MULTI/EXEC。先 WATCH 锁 key，然后读取 value 判断是否是当前线程的锁，如果是就开启事务删除。执行 EXEC 时，如果这个 key 在期间被其他客户端修改过，事务会失败，从而避免误删别人的锁。

另外也可以用数据库实现分布式锁，比如基于唯一索引、行锁或者 select for update。但是这是另一套锁实现方式，不是直接解决 Redis 中 get + del 的原子性问题。实际项目里 Redis 分布式锁释放锁最常用、最推荐的还是 Lua 脚本。
```

```java
        log.error("不允许重复下单！");
        return;
    }
    try {
        proxy.createVoucherOrder2(voucherOrder);
    } finally {
        redisLock.unlock();
    }
}
```

# 六：社交消息异步解耦与通知中心

## 背景

在博客点赞、评论、关注等社交场景中，如果同步处理通知逻辑，会导致主链路变长且耦合度升高，因此项目中引入 RabbitMQ 将通知逻辑异步化。

## 一：事务提交后发送消息

```java
public void publishAfterCommit(SocialNotificationMessage message) {
    if (TransactionSynchronizationManager.isActualTransactionActive()) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                send(message);
            }
        });
        return;
    }
    send(message);
}
```
